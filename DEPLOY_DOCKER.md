# Развёртывание Docker и AD

## 1. Подготовка

На Linux-сервере нужны Docker Engine, Compose 2.24.4+ и Python 3 только для генерации конфигурации. Приложение запускается в контейнере Python 3.12. Откройте пользователям HTTPS 443 в офисной сети/VPN; база и backend не публикуют порты хоста. DNS сервера/контейнеров должен разрешать FQDN контроллера AD. От приложения к контроллеру требуется TCP 636.

Скопируйте проект на сервер, перейдите в папку с `compose.yaml`, выполните:

```sh
python3 deploy/configure.py
```

Скрипт создаёт `.env` с уникальными паролем PostgreSQL, ключом шифрования настроек AD и ключом первого запуска. Повторный запуск не перезаписывает существующий файл. Не публикуйте `.env`, не присылайте его в чат, сохраните защищённую резервную копию. Для доступа к файлу оставьте права `600`.

Измените `PUBLIC_ORIGIN` на точный адрес портала без завершающего `/`, например `https://peregovornii.ugmkstroy.ru`. Если используется нестандартный порт, включите его в адрес. Не меняйте `POSTGRES_PASSWORD` у уже созданной базы только редактированием `.env`: пароль роли PostgreSQL нужно менять согласованно.

## 2. Сертификаты

Установите файлы в `deploy/certs/`:

| Файл | Назначение |
| --- | --- |
| `portal.crt` | Сертификат HTTPS сайта и промежуточные сертификаты в PEM |
| `portal.key` | Закрытый ключ HTTPS в PEM, доступный контейнеру Nginx |
| `ad-ca.pem` | Цепочка доверенных корпоративных CA, выпустивших сертификат контроллера AD |

Скрипт генерации создаёт `ad-ca.pem` из публичных корней системы, чтобы разрешить локальный запуск. Для внутреннего AD замените файл цепочкой вашего корпоративного CA. В настройках AD используйте DNS-имя, совпадающее с сертификатом контроллера. Проверка сертификата обязательна, отключения проверки в интерфейсе нет.

Приложение работает с UID 10001: публичный `ad-ca.pem` должен быть ему доступен на чтение. Закрытый ключ HTTPS в образ приложения не включается, контейнер приложения его не монтирует.

## 3. Запуск и первый администратор

```sh
docker compose config --quiet
docker compose up -d --build
docker compose ps
docker compose logs --tail=100 app proxy
```

База проходит healthcheck; приложение применяет идемпотентную схему под блокировкой и затем начинает принимать запросы. Откройте адрес из `PUBLIC_ORIGIN`. В форме первого запуска укажите `BOOTSTRAP_TOKEN` из `.env`, логин и пароль локального администратора (не менее 12 символов). После успешного создания повторная первоначальная настройка закрывается на уровне базы, включая параллельные запросы.

Для повторного входа используйте флажок «Войти как локальный администратор». Не публикуйте ключ первого запуска. После завершения настройки он не позволяет создать ещё одного локального администратора.

## 4. Подключение AD

В «Управление → Подключение к Active Directory» заполните:

- FQDN контроллера, например `dc01.ekatcity.ekat-city.com`;
- домен/realm `EKATCITY.EKAT-CITY.COM`;
- Base DN, например `DC=ekatcity,DC=ekat-city,DC=com`, либо OU разрешённых сотрудников;
- DN или UPN отдельной служебной учётки с правами чтения каталога;
- пароль этой служебной учётки.

Нажмите «Проверить подключение», затем «Проверить и сохранить». Проверка выполняет служебный bind и чтение Base DN. Фактический вход сотрудника нужно дополнительно проверить его учётной записью: тест служебного подключения не подтверждает пароль сотрудника. Пароль служебной учётки обратно в браузер не возвращается; пустое поле при сохранении сохраняет предыдущий пароль.

Сотрудники входят через форму: `login`, `login@domain` либо `DOMAIN\login`. Для короткого DOMAIN используется первый сегмент realm; при отличающемся NetBIOS-имени используйте короткий логин или полный UPN. Поиск и вход ограничены Base DN и исключают отключённые учётки. Вход проверяется bind с точным DN сотрудника. Пароли не передаются по незашифрованному LDAP и не записываются в журнал.

Сохранение настроек AD завершает существующие доменные сессии, чтобы не сохранить доступ от предыдущего каталога. Локальные сессии сохраняются.

## 5. Роли

В разделе «Права сотрудников» найдите сотрудника по имени/почте (от двух символов), отметьте «Администратор» и/или «Бронирование по поручению», сохраните. Снимите обе отметки, чтобы вернуть обычные права сотрудника. Роль действует только в приложении, а не в домене AD. Роли привязаны к objectGUID, отображаемое имя сохраняется для списка назначений и аудита.

У сотрудника должны быть заполнены displayName; почта полезна для поиска, но не обязательна. Смена прав применяется на следующем запросе даже для открытой сессии. Снятие последнего доменного администратора не блокирует аварийную локальную учётку. Изменение ролей, настроек и пароля записывается в аудит.

## Почтовые уведомления

В «Управление → Почтовые уведомления» укажите адрес корпоративного SMTP, порт, режим соединения, адрес отправителя и при необходимости логин/пароль. По умолчанию отправка выключена. Поддерживаются STARTTLS (обычно 587), SSL/TLS (обычно 465) и внутренний relay без авторизации (обычно 25). Парольная авторизация разрешена только по TLS. Для relay почтовый администратор должен разрешить отправку с сервера/сети контейнеров от выбранного адреса. Открывать входящий SMTP-порт приложения не требуется: нужен исходящий доступ к почтовому серверу.

1. Заполните настройки и адрес для теста.
2. Нажмите «Отправить тестовое письмо» и проверьте почтовый ящик, включая нежелательную почту. Тест использует значения формы и отправляет только одно письмо на явно указанный адрес, без сохранения формы.
3. Отметьте «Включить отправку уведомлений» и сохраните настройки. Сохранение не проверяет SMTP автоматически: используйте тестовую отправку.
4. Создайте встречу с участниками AD и проверьте статусы в таблице «Последние уведомления».

Пароль SMTP хранится зашифрованным тем же `SETTINGS_KEY`, что и настройки AD. Он не возвращается в браузер; пустое поле сохраняет старый пароль для того же логина. Для смены логина введите новый пароль. Для relay оставьте логин пустым — ранее сохранённый пароль будет удалён из настроек.

Проверка сертификата TLS обязательна. По умолчанию используются публичные корневые сертификаты и дополнительная цепочка из `AD_CA_FILE` (в Compose — `deploy/certs/ad-ca.pem`). Если почтовый сервер использует другой корпоративный CA, добавьте его в этот PEM-бандл либо смонтируйте отдельный PEM и задайте `SMTP_CA_FILE` в окружении контейнера приложения. После замены сертификатов перезапустите приложение.

Адрес берётся из атрибута `mail`, а не из UPN: они могут различаться. Письма адресуются организатору и всем участникам; автор бронирования по поручению получает письмо, только если сам является организатором/участником. Повторяющиеся адреса объединяются без учёта регистра. Если адрес в AD отсутствует или некорректен, бронь создаётся, а уведомление отмечается как пропущенное. У локального администратора доменного адреса нет; для полноценного почтового сценария используйте сотрудника AD. Адреса фиксируются в данных встречи при выборе сотрудников; изменение mail в AD не переписывает ранее сохранённые бронирования автоматически.

События: создание, изменение (включая добавление участника), отмена, продление и досрочное завершение. Для серии письмо формируется по каждому экземпляру. Исключённый участник получает отдельное письмо с прежней темой и временем, без новой повестки и новых участников. Блокировки помещения не рассылаются. Включение почты не рассылает всю старую историю: очередь создаётся только для последующих событий.

Бронь и запись в почтовой очереди сохраняются одной транзакцией. SMTP работает в фоновом потоке приложения; отказ почты не отменяет бронь. Очередь PostgreSQL сохраняется после перезапуска контейнера; отдельный брокер сообщений не нужен. Попытки повторяются с увеличением интервала (от 30 секунд до 1 часа), максимум 10 раз, затем запись переходит в ошибку. Администратор может нажать «Повторить» для ошибки актуальной версии встречи. Старая неотправленная версия заменяется новым событием, в том числе при отключённой отправке, чтобы исключённые участники не получили устаревшие сведения. При выключении почты оставшаяся очередь приостанавливается и продолжает работу после включения; уже начатая SMTP-отправка может завершиться.

«Принято SMTP» подтверждает приём письма SMTP-сервером, а не доставку в конечный ящик. Ошибки дальнейшей маршрутизации/спам-фильтров проверяются в почтовой системе. При аварии между приёмом письма сервером и записью результата в БД возможна повторная доставка; используется стабильный Message-ID, но гарантии exactly-once у SMTP нет. Пароли и текст диагностик SMTP в журнал не записываются, сохраняются тип ошибки и числовой код.

Вложения `.ics` предназначены для ручного импорта. Это информационные письма, без автоматической синхронизации календаря, ответов на приглашение и EWS/Graph. Письма содержат сведения о встречах, поэтому используйте корпоративный SMTP и согласованную почтовую политику. История очереди доступна только администраторам, очищается командой `prune` по сроку 12 месяцев; неотправленные записи сохраняются.

Технические источники: [Python smtplib](https://docs.python.org/3.12/library/smtplib.html), [PostgreSQL: блокировки и SKIP LOCKED](https://www.postgresql.org/docs/16/sql-select.html).

## 6. Резервное копирование и восстановление

```sh
python3 deploy/backup.py /secure-backups/portal-2026-11-10.dump
```

Скрипт создаёт PostgreSQL custom-format dump и отказывается перезаписывать существующий файл. Отдельно защищённо сохраняйте `.env`, сертификаты и конфигурацию: без исходного `SETTINGS_KEY` пароль AD из резервной БД не расшифровать. Дамп содержит хеш локального пароля, сессии и другие закрытые данные. Храните его вне сервера с ограниченным доступом; запускайте резервное копирование ежечасно, контролируйте ошибки и проверяйте восстановление.

Восстановление на отдельном сервере с теми же `.env` и сертификатами, из shell Linux:

```sh
docker compose up -d db
# Дождитесь healthy у db: docker compose ps
docker compose exec -T db pg_restore -U portal -d portal --clean --if-exists < /secure-backups/portal-2026-11-10.dump
docker compose exec -T db psql -U portal -d portal -c 'DELETE FROM portal_sessions;'
docker compose up -d --build
```

Восстановление заменяет данные целевой базы — применяйте только к выбранной установке. Дамп и ключ должны относиться к одной установке. Проверяйте вход, список броней, роли, отмену и создание встречи после восстановления. RTO 4 часа / RPO 1 час подтверждаются эксплуатационным учением, самим наличием скрипта они не обеспечены.

Для хранения истории 12 месяцев добавьте ежедневный запуск:

```sh
docker compose exec -T app python -m server.manage prune
```

Если локальный пароль потерян, оператор сервера может сбросить его с интерактивным вводом без пароля в командной строке:

```sh
docker compose exec app python -m server.manage reset-local-password
```

После смены/сброса пароля все локальные сессии завершаются.

## 7. Обновление и остановка

Сначала сделайте резервную копию, затем замените исходники и выполните `docker compose up -d --build --force-recreate`. Это пересоздаст сервисы с кратким перерывом; Nginx заново разрешит адрес контейнера приложения. Миграции новой версии применяются при запуске. Перед откатом версии проверяйте совместимость схемы; для несовместимого отката потребуется восстановление согласованной резервной копии.

`docker compose down` останавливает сервисы, сохраняя базу. **Не добавляйте `-v` к рабочей установке:** это удалит volume PostgreSQL. Демонстрационные данные localStorage в рабочую базу не импортируются.

## 8. Локальная проверка и тесты

Для локальной проверки используйте `docker compose -f compose.yaml -f compose.local.yaml up -d --build` и http://localhost:8080. Перед созданием `.env` проверьте, что он ещё не существует. HTTPS-сертификат сайта для локального режима не требуется. Compose 2.24.4+ нужен для корректного переопределения опубликованных портов через `!override`.

Полный набор тестов с отдельной временной PostgreSQL:

```sh
docker compose -f compose.test.yaml up --build --abort-on-container-exit --exit-code-from tests
docker compose -f compose.test.yaml down
```

Успешные тесты с имитацией LDAP не заменяют проверку реального AD, корпоративных сертификатов, DNS, VPN и прав служебной учётки. После настройки проверьте обычного пользователя, назначенного администратора, отзыв роли и отключённую учётку.

Источники по используемым механизмам: [Docker Compose: порядок запуска](https://docs.docker.com/compose/how-tos/startup-order/), [Compose: сервисы и override](https://docs.docker.com/reference/compose-file/services/), [ldap3: TLS и проверка сертификатов](https://ldap3.readthedocs.io/en/latest/ssltls.html).
