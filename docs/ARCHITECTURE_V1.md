# Портал бронирования переговорных · УГМК-Застройщик

Первая версия приложения, 10.11.2026. Основание: актуальный `TZ_peregovornii_v0_2.docx` и последние ответы в обсуждении «Требования и ТЗ».

## Принятые решения

- Внутренний сервер Ubuntu 22.04, доступ только из офиса и VPN.
- Адрес: `https://peregovornii.ugmkstroy.ru`; AD: `ekatcity.ekat-city.com`, краткое имя `ekatcity`.
- Две комнаты: «Переговорная 1 этаж» и «Переговорная 2 этаж».
- Ежедневно 07:00–21:00, Asia/Yekaterinburg; 15 минут–4 часа, шаг 15 минут, горизонт 60 дней, без буфера.
- Администраторы — AD-группа `ekatcity\bron`. Это группа, не имя служебной учётной записи приложения.
- Только члены `secretary` могут назначать другого организатора. Администратор без `secretary` не получает это право.
- Серии ежедневно или по дням недели; исключение конфликтных дат только явное; изменение одного экземпляра или будущей части серии.
- Outlook/локальный Exchange: ссылка и ручной импорт .ics одного экземпляра. Нет автоматических приглашений, синхронизации, EWS/Graph и видеосвязи.
- Сведения о встречах и аудит хранятся 12 месяцев. Цели восстановления: RTO 4 часа, RPO 1 час; их достижение подтверждается учением на сервере.

## Реализация

Одно приложение: статический интерфейс без сборки + FastAPI/Python 3.10+ + PostgreSQL 14+. Перед ним Apache с mod_auth_gssapi. Микросервисы и облачные сервисы для рабочей установки не требуются. Обоснование выбора: Ubuntu уже согласована; приложение, reverse proxy и база сопровождаются обычными systemd-службами.

- `dist/`: интерфейс, фирменный логотип, стили; все ресурсы локальные.
- `server/`: API, правила, права, каталог AD и схема PostgreSQL.
- `deploy/`: шаблоны Apache, systemd, окружения, резервного копирования и хранения.
- `tests/`: проверки правил, HTTP-защиты и интеграционные проверки с PostgreSQL.
- `qa/verify_single_postgres.py`: дополнительный тестовый адаптер для автономного PostgreSQL, не часть рабочего приложения.
- `requirements.lock.txt`: зафиксированные версии библиотек, использованные при проверке. Они поддерживают Python 3.10.
- `STATUS.md`: фактические проверки и оставшиеся проверки корпоративной инфраструктуры.

### Вход и AD

Apache выполняет Kerberos/Negotiate, при необходимости Basic-аутентификацию через Kerberos по HTTPS. Приложение не получает и не сохраняет пользовательские пароли. Apache удаляет присланные клиентом заголовки и передаёт проверенную личность и секрет доверенного прокси. Uvicorn доступен только через Unix-сокет с ограниченными правами. **Нельзя публиковать backend напрямую или доверять заголовкам от внешнего клиента.**

Справочник читается по LDAPS с проверкой сертификата. Идентичность — objectGUID. Членство во вложенных группах проверяется запросом AD на каждом обращении. При отзыве `secretary` дополнительные права автора прекращаются. Отказ AD возвращает ошибку, а не вымышленные данные. Для большого каталога задайте AD_BASE_DN, ограниченный областью сотрудников.

Точные DN групп, контроллер AD, служебная учётная запись чтения каталога, корпоративный CA, SPN/keytab и разрешённые сети задаются при установке. Их нет в исходных требованиях; шаблоны содержат явные placeholders. Реальный автовход на Edge/Firefox и вход личных устройств проверяются в корпоративной среде.

### Целостность данных

Все записи и изменения сериализуются транзакционной advisory-блокировкой PostgreSQL. Для небольшого числа пользователей это простое решение. Дополнительно GiST exclusion constraint запрещает пересечение активных интервалов; комната представлена одиночным `int4range`, время — `tstzrange` с границами `[)`. Дополнительное расширение btree_gist не требуется. Блокировки комнат подчиняются тому же ограничению. Ограничение отложено до COMMIT, чтобы атомарно редактировать несколько экземпляров серии.

Запросы имеют ключ идемпотентности и fingerprint. Повтор неизменённого запроса не создаёт новую запись. Версия каждого изменяемого экземпляра защищает от перезаписи устаревших изменений. Ошибка транзакции не выдаётся за успех. Права и редактирование проверяются сервером, данные посторонним отфильтровываются до сериализации.

## Демонстрация и рабочий режим

Опубликованный просмотр — **только демонстрация**. В нём вымышленные сотрудники и брони, хранящиеся в localStorage данного браузера. Переключатель роли служит для проверки интерфейса. Данные между браузерами не общие, реальный AD не подключён; вводить рабочие конфиденциальные данные в демонстрацию не следует.

Внутренний сервер сам отдаёт `/config.js` с `demo:false`. Интерфейс использует `/api`, а демонстрационный модуль не загружается. В рабочем режиме нет переключателя ролей и нет демонстрационного fallback. **Не размещайте каталог dist отдельным статическим сайтом вместо запуска server.app:** тогда получится демонстрация, а не общий корпоративный сервис. Apache должен проксировать весь сайт в приложение.

## Запуск для разработчика

Полная пошаговая инструкция переноса на корпоративный сервер — следующий этап. Состав пакета уже подготовлен под неё. Базовая последовательность для администратора, знакомого с окружением:

1. Создать виртуальное окружение Python, установить `requirements.lock.txt`.
2. Создать отдельную БД и роль приложения в PostgreSQL. Подготовить значения из `deploy/portal.env.example`.
3. Передать переменные окружения процессу и выполнить `python -m server.manage migrate` от владельца схемы.
4. Настроить Apache/GSSAPI, сертификаты, keytab и Unix-сокет по шаблонам. Установить systemd-службу приложения.
5. Настроить резервные копии на отдельное хранилище, уведомление о сбое backup и ежедневную очистку. Проверить восстановление.
6. Пройти приёмку A01–A17 из ТЗ в корпоративном контуре. До этого не считать сервис введённым в эксплуатацию.

Запуск тестов без базы: `python -m pytest tests/test_domain.py tests/test_http_security.py -q` (нужны pytest и httpx).

Для полного набора создайте **отдельную одноразовую БД**, установите `TEST_DATABASE_URL` и запустите `python -m pytest tests -q`. Интеграционный набор очищает таблицы; **не указывайте рабочую БД**. Без переменной интеграционные тесты пропускаются. Справочник в автотестах заменяется тестовыми записями, реальный AD они не проверяют.

## Фирменное оформление

Логотип извлечён из предоставленного «Брендбук 2.0_УГМК_Застройщик.pdf», стр. 3, из варианта на белой подложке. Основной оранжевый взят из RGB-представления CMYK 0/60/100/0 в PDF: `#EF7C00`; тёмный — `#1A1A18`. Цветовые состояния дополнены текстом.

Брендбук задаёт TT Norms, но отдельных лицензированных веб-файлов шрифта в материалах нет. Используется локальный TT Norms при наличии, иначе Arial. Для полного совпадения типографики необходимо добавить разрешённые к использованию woff2 и обновить @font-face. Встроенные подмножества из PDF в веб-шрифты не преобразовывались.
